# Contributing to Hydroponer

The project is currently in its documentation and design phase. The most valuable contributions right now are corrections to the domain knowledge and challenges to the design decisions — not code.

## What is most useful right now

**Horticultural review.** If you grow hydroponically and something in [the domain model](docs/07-domain-model.md) is wrong — a DLI band, a spacing figure, a pH range, a failure mode — say so, and say where the correct figure comes from. This is the highest-value contribution available.

**Regional price data.** [Cost estimation](docs/09-cost-estimation.md) depends on a per-country multiplier surveyed against a basket of common items. Real prices from real shops in any country are directly useful.

**Design challenges.** If an [architecture decision](docs/adr/) is wrong, open an issue arguing the case. ADRs are meant to be contested before they are built on.

**Safety review.** Anything in the [structural](docs/07-domain-model.md#77-structural-model) or [safety constraint](docs/08-layout-generation.md#86-safety-constraints) rules that is unsafe, or any hazard the model does not account for.

## Ground rules for domain data

Every value in the catalog must be sourced. A pull request that changes a number must say where the number comes from: an extension service publication, peer-reviewed literature, or a manufacturer specification.

Values generated by a language model are not acceptable in the catalog, ever. This is the same rule the product applies to itself.

## Issues

Use the templates. For a domain correction, include the current value, the proposed value, and the source. For a bug, include the plan id if there is one — it resolves to a full trace of what produced the output.

## Pull requests

Once code exists:

- One logical change per pull request
- Type check, lint, and tests must pass
- Changes to `packages/prompts`, `packages/catalog`, or model configuration additionally require a passing evaluation run against the golden set
- New engine behaviour needs property tests, not just examples
- Safety-relevant changes need a second reviewer

Commit messages follow Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`).

## Documentation

Documentation is part of the product, not an afterthought. A change to how the system works includes the change to the document that describes it, in the same pull request.

Write plainly. Explain why, not only what — the existing documents are written to be argued with, and new ones should be too.

## Code of conduct

Be decent. Assume good faith. Disagree about the work, not the person. Unacceptable behaviour can be reported to the maintainers.
