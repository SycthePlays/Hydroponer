# 20. 3D Visualisation

Every plan ships with an interactive 3D view of the designed system. The user can orbit around it, spin it, zoom into any component, and look at the build from any angle before buying a single part.

This is not decoration. A 2D plan answers "does it fit". A 3D view answers "what am I actually building" — and for a person who has never seen a hydroponic system in person, that is the difference between a drawing and an understanding.

---

## 20.1 What the user gets

| Capability | Detail |
|---|---|
| **Orbit** | Drag to rotate the whole scene around its centre; the design turns through a full 360° horizontally and from floor level up to a top-down view |
| **Spin** | Momentum-based rotation — flick and the model keeps turning, so the user can watch it go round without holding the pointer |
| **Zoom** | Wheel, pinch, or buttons; from the whole space down to a single net pot |
| **Pan** | Move the camera target to inspect a corner without losing orientation |
| **Component focus** | Tap any component to fly the camera to it, isolate it, and show its BOM lines and install steps |
| **Layer isolation** | Show or hide structure, plumbing, electrical, lighting, plants, and the room shell independently |
| **Exploded view** | A slider that separates the assembly along its build axis, so the user can see how parts fit together |
| **Build playback** | Step through the tutorial phases and watch the system assemble itself, phase by phase |
| **Growth preview** | Toggle plants between transplant size and mature size, which is how a user discovers that their canopy will hit the shelf above |
| **Measurement mode** | Click two points to get the distance between them |
| **Preset cameras** | Front, side, top, isometric, and "standing in the doorway" — the last matching the angle of the user's own photo |

Everything above works on a mid-range phone, which is the constraint that shapes the rest of this document.

---

## 20.2 Where the 3D comes from

Nothing is modelled by hand, and nothing is generated by an AI model. The scene is a direct, deterministic projection of the solved layout.

```
Layout (from the engine)              3D scene
──────────────────────────────────────────────────────────────
bounds_mm + surfaces          ->      room shell: floor, walls, ceiling
PlacedComponent[]             ->      instanced meshes from the part library
  position_mm, size_mm,               placed at exact coordinates,
  rotation_deg                        scaled to their real dimensions
plumbing_runs[]               ->      swept tubes along the run polyline
electrical_runs[]             ->      cable curves with drip loops
plant sites + crop record     ->      instanced plant meshes at spacing,
                                      scaled to the crop's mature height
walkways[]                    ->      floor overlay
warnings[]                    ->      anchored annotation markers
light.windows[]               ->      window openings and a sun direction
```

Because the scene is derived, it is guaranteed to agree with the 2D plan, the bill of materials, and the tutorial. There is one source of truth — the layout — and three renderings of it. A component cannot appear in the 3D view without existing in the BOM, because the renderer walks the BOM to build it.

### The part library

Each catalog item that has physical presence carries a `model_ref` pointing to a low-poly glTF primitive: a channel section, a net pot, a tote, a bucket, a pump, an LED bar, a tower segment, a frame member.

Rules for the library:

- **Parametric, not per-SKU.** One channel model scales along its length rather than one model per length. The library stays in the dozens of assets, not the thousands.
- **Low-poly by policy.** A fixed triangle budget per asset, because the scene assembles hundreds of instances on a phone.
- **Draco-compressed glTF**, served from the CDN, cached aggressively — the library changes only when the catalog does.
- **Shared materials.** A small palette across the whole library, so the renderer can batch aggressively.
- **A generic fallback.** Any catalog item without a model renders as a labelled box at its true dimensions. A missing asset degrades the view; it never breaks it or hides a part.

## 20.3 Rendering approach

**Client-side, WebGL, via Three.js and React Three Fiber.**

The scene description is small — a few hundred component placements, computed server-side — so the server sends JSON and the browser assembles the scene from the cached part library. No per-plan asset is generated, stored, or transferred.

| Technique | Why |
|---|---|
| Instanced meshes | 96 net pots and 96 plants are two draw calls, not 192 |
| Baked ambient occlusion, no realtime shadows by default | Shadows are the biggest mobile cost for the least comprehension gain |
| One directional light plus hemisphere fill | Enough to read form; sun direction from the scene's window orientation where known |
| Frustum culling and level of detail | Distant plants drop to billboards |
| `preserveDrawingBuffer: false`, capped device pixel ratio | Memory and fill-rate discipline on phones |
| Render on demand | The frame loop stops when nothing moves; a static scene costs no battery |

### Performance targets

| Device class | Target |
|---|---|
| Desktop | 60 fps, full detail |
| Recent phone | 60 fps at reduced plant detail |
| Mid-range Android | 30 fps minimum, LOD aggressive |
| Low-end, or no WebGL | 2D plan only, with a clear explanation |

Scene payload is capped, and a design with many hundreds of plant sites switches to grouped plant meshes rather than individual ones.

## 20.4 Progressive enhancement

The 3D view is an enhancement over the 2D plan, never a replacement for it, and never a dependency.

```
WebGL available          -> 3D viewer, 2D plan available on a tab
WebGL unavailable        -> 2D plan, with a note that 3D needs a newer browser
Reduced motion preferred -> No auto-spin, no camera fly-through; all motion on demand
Screen reader in use     -> The structured component list is the primary surface;
                            the canvas is aria-hidden
Print or PDF             -> A rendered isometric still image plus the 2D plan
Slow connection          -> 2D first; the part library loads in the background
                            and the 3D tab activates when it is ready
```

The 2D plan remains the canonical drawing. It is what prints, what a builder holds, and what a screen reader reads. The 3D view is what makes the plan *understood*.

## 20.5 Accessibility

A canvas is opaque to assistive technology, so the 3D view is built with a parallel non-visual path rather than an apology.

- **Keyboard control.** Arrow keys orbit, `+` and `-` zoom, `Tab` cycles components, `Enter` focuses one, `Escape` returns to the overview. Every pointer gesture has a key equivalent.
- **Structured equivalent.** Beneath the canvas, a navigable list of every component with its position, dimensions, and connections — the same data the renderer consumes. This is the accessible primary, not a summary.
- **Announcements.** Focusing a component announces its name, size, position, and role.
- **Reduced motion.** `prefers-reduced-motion` disables momentum spin, auto-rotation, and camera transitions; the camera cuts instead of flying.
- **No colour-only meaning.** Component types carry labels and distinct silhouettes; warnings carry an icon and text, not a red tint.
- **Contrast and legibility.** In-scene labels render as DOM overlays rather than canvas text, so they inherit the page's font size and contrast settings.

## 20.6 Scene contract

The server computes the scene description; the client renders it. The engine's layout is the input, so the scene is deterministic — the same plan always produces the same scene.

```ts
type Scene3D = {
  version: string
  units: 'mm'
  room: {
    bounds_mm: { w: number; d: number; h: number }
    floor_material: string
    wall_materials: string[]
    openings: Opening[]          // windows and doors, with orientation
    sun_direction: Vec3 | null   // null when orientation is unknown
  }
  nodes: SceneNode[]
  annotations: Annotation[]      // warnings and callouts, anchored to node ids
  phases: PhaseGroup[]           // node ids per build phase, for playback
  cameras: NamedCamera[]         // front, side, top, isometric, doorway
}

type SceneNode = {
  id: string                     // matches PlacedComponent.id
  model_ref: string | null       // glTF asset id; null renders the fallback box
  bom_line_ids: string[]         // what this node costs
  tutorial_step_ids: string[]    // what installs it
  transform: {
    position_mm: Vec3
    rotation_deg: Vec3
    scale: Vec3                  // parametric stretch along the scalable axis
  }
  size_mm: { w: number; d: number; h: number }
  layer: 'structure' | 'plumbing' | 'electrical' | 'lighting' | 'plants' | 'shell'
  label: string
  instances?: InstanceSet        // for repeated geometry: net pots, plants
}
```

`bom_line_ids` and `tutorial_step_ids` on every node are what make the view useful rather than pretty: tapping a bench in 3D shows what it costs and which steps build it, and a tutorial step can highlight exactly what it is talking about.

## 20.7 What it is not

- **Not a modelling tool.** The user cannot add, delete, or freely move geometry. Layout changes go through the engine's constrained adjustment flow, and the 3D view re-renders from the new layout.
- **Not photorealistic.** The goal is comprehension, not a render. Clear silhouettes, honest proportions, readable labels.
- **Not a replacement for the plan.** See §20.4.
- **Not AI-generated.** No model produces geometry, textures, or placements. The [no-invented-numbers rule](06-ai-pipeline.md#the-no-invented-numbers-rule) applies to geometry exactly as it applies to prices — a mesh in the wrong place is a dimension lie told visually.

## 20.8 Testing

| Check | Method |
|---|---|
| Scene matches layout | Every `PlacedComponent` produces exactly one node; positions match to the millimetre |
| Scene matches BOM | Every node's `bom_line_ids` resolve; every physical BOM line appears in at least one node |
| No intersections | Automated check that no two node bounding boxes overlap, mirroring the solver's constraint |
| Determinism | The same layout produces a byte-identical scene description |
| Visual regression | Rendered stills of the golden-set layouts, compared per release |
| Performance | Frame time measured on a mid-range device profile in CI, with a budget that fails the build |
| Accessibility | Keyboard traversal and the structured equivalent tested alongside the rest of the plan page |
| Fallback | The no-WebGL path is exercised in end-to-end tests, not assumed |
